# Research: the 2026 Android-first release path

Charting research for the wayfinder map. Date: **2026-09-30**. Version-sensitive — Play policy, Expo SDK 57, and the ads library all move fast.

Question: what are the factual 2026 requirements for shipping this app Android-first — the Google Play new-personal-account production gate, the EAS Build / FCM v1 push path, `react-native-google-mobile-ads` compatibility with Expo SDK 57 / RN 0.86, and the store privacy disclosures an app needs for push tokens + AdMob?

## Recommendation

1. **Account — the gate is the long pole, so start it first.** On a **personal** developer account created after **13 Nov 2023**, you cannot publish until you run a **closed test with ≥12 testers opted in continuously for the preceding 14 days**, then *Apply for production* (review "usually takes seven days or less"). If you can register as an **organization** account instead, you skip this gate entirely and can publish directly. Either way, start the closed test on day one — it is calendar-bound and nothing else in the release plan is.
2. **Build — plan for dev builds, not Expo Go.** `expo-notifications` remote push is **not available in Expo Go on Android since SDK 53**, and AdMob requires native code, so the working loop is an **EAS development build** (`developmentClient: true`). Ship the store artifact from the **production** profile — an Android App Bundle (`.aab`).
3. **Push — FCM HTTP v1 via Expo.** Create a Firebase project, upload the **FCM v1 service-account key JSON** to EAS credentials (`eas credentials` → Android → production → Google Service Account), drop **`google-services.json`** at the project root and point `expo.android.googleServicesFile` at it. Then `expo-notifications` + the free Expo push service issues an `ExpoPushToken`; the same library can also talk to FCM/APNs directly.
4. **Ads — pin `17.0.0` today.** `react-native-google-mobile-ads` **17.1.0 and 17.2.0** break Android builds in the Expo config-plugin setup (**issue #903, still open** on 2026-09-30). `17.0.0` is unaffected; the alternative is a two-line `patch-package`. v17 is a good fit for SDK 57: it **requires RN 0.86+, the New Architecture, iOS 15.1, Android API 24**.
5. **Disclosures — do both forms before submitting.** Play **Data safety** (mandatory on every track except internal-testing-only) and Apple **App Privacy** must both reflect third-party SDK behaviour. Push tokens and AdMob both land under **"Device or other IDs" / "Device ID"**; AdMob additionally drives **Advertising or marketing + Analytics** purposes and, on iOS, the **tracking / ATT** flow.

## (a) Google Play production access for a new personal account

- **Who it applies to:** personal accounts created **after 13 Nov 2023**. The article is explicitly scoped to them, so **organization accounts are not subject to it**; internal-testing-only apps and private apps are also outside the Data safety/testing gate framing. https://support.google.com/googleplay/android-developer/answer/14151465
- **The requirement (current wording):** "At least 12 testers must be opted in to your closed test when you apply for production access, and they must have been opted in **continuously for the preceding 14 days**." Minimum **12 testers / 14 consecutive days**. https://support.google.com/googleplay/android-developer/answer/14151465
- **Continuous means continuous:** testers who opt out before 14 days don't count, and re-opting restarts their individual clock — the 14 days must be consecutive. https://support.google.com/googleplay/android-developer/answer/14151465
- **Minimal path:** complete app setup → run a **closed test** (the only track that satisfies the requirement) with ≥12 continuously-opted-in testers for 14 days → **Apply for production** from the Play Console Dashboard, answering three sections (about your closed test, about the app, about production readiness). Review "usually takes seven days or less." https://support.google.com/googleplay/android-developer/answer/14151465
- **Tracks:** *Internal testing* has no requirements but is optional and does **not** satisfy the gate; *Open testing* only becomes available **after** you gain production access; *Production* requires the closed test. https://support.google.com/googleplay/android-developer/answer/14151465
- **Tester definition:** testers are the Google accounts you add to the closed test's email list who opt in via the Play link and keep the app installed/opted in. Google's guidance stresses recruiting real, active testers from your target audience and summarising their feedback in the application. https://support.google.com/googleplay/android-developer/answer/14151465

## (b) EAS Build in 2026, FCM v1 credentials, and `expo-notifications`

- **Default `eas.json` profiles** generated by `eas build:configure`: `development` (`"developmentClient": true, "distribution": "internal"`), `preview` (`"distribution": "internal"`), `production` (`{}`). Omitting `--profile` defaults to `production`. https://docs.expo.dev/build/eas-json/
- **Development vs production builds:** a development build depends on `expo-dev-client`, includes developer tools, and is never submitted to a store; a production build is store-bound and *cannot* be installed directly on a device/simulator unless you set `"buildType": "apk"`. `.aab` is the recommended Play artifact. https://docs.expo.dev/build/eas-json/
- **Expo Go cannot test this app's push:** "Push notifications (remote notifications) functionality provided by `expo-notifications` is unavailable in Expo Go on Android from SDK 53. A development build is required." https://docs.expo.dev/versions/latest/sdk/notifications · https://expo.dev/changelog/sdk-53
- **FCM v1 credentials — two pieces:**
  1. **Service-account key JSON** (the sender credential) uploaded to EAS: `eas credentials` → `Android` → `production` → `Google Service Account` → manage/set up the **FCM V1** key, or upload it under Project settings → Credentials on expo.dev. Keep it out of source control. https://docs.expo.dev/push-notifications/fcm-credentials/
  2. **`google-services.json`** (the client credential) from the Firebase console, placed at the project root, with `expo.android.googleServicesFile: "./google-services.json"` in `app.json`. This file is safe to commit. https://docs.expo.dev/push-notifications/fcm-credentials/
- **Known FCM gotcha:** if the `google-services.json` API key is restricted, it must allow the **FCM Registration API** and **Firebase Installations API**, and its application restriction must use the **Play App Signing** SHA-1 (not the upload key) — otherwise the Firebase Installations API returns `403 PERMISSION_DENIED` and the app never gets a push token. https://docs.expo.dev/push-notifications/fcm-credentials/
- **What `expo-notifications` needs for remote push:** install `expo-notifications` + `expo-constants`, add the `expo-notifications` config plugin, request permission, create an Android notification channel, then call `Notifications.getExpoPushTokenAsync({ projectId })` (projectId from `expo-constants`). Send via `https://exp.host/--/api/v2/push/send`, or use FCM/APNs directly (`getDevicePushTokenAsync`). Android 13 needs the `POST_NOTIFICATIONS` runtime permission (handled via `requestPermissionsAsync`). https://docs.expo.dev/push-notifications/push-notifications-setup/
- **FCM HTTP v1 is the only FCM path** in 2026 (the legacy server-key API was removed in 2024), which is exactly why the service-account key above is required. https://docs.expo.dev/push-notifications/fcm-credentials/

## (c) `react-native-google-mobile-ads` vs Expo SDK 57 / RN 0.86

- **Latest release: `17.2.0` (2026-09-25).** `17.1.0` was 2026-09-23; `17.0.0` was 2026-09-18. https://github.com/invertase/react-native-google-mobile-ads/blob/main/CHANGELOG.md
- **v17 platform floor (breaking):** "v17 requires React Native 0.86.0+, the New Architecture, iOS 15.1, and Android API 24. Legacy Architecture is unsupported." That matches **Expo SDK 57** (RN 0.86, New Architecture default). https://github.com/invertase/react-native-google-mobile-ads/blob/main/CHANGELOG.md
- **Config-plugin bug #903 — OPEN as of 2026-09-30.** Filed 2026-09-26: on Expo projects configured through the config plugin (no top-level `react-native-google-mobile-ads` key in `app.json`), Android builds fail with "Cannot get property `googleMobileAdsJson` on extra properties extension as it does not exist" during Gradle configuration. **17.0.0 is not affected**; **17.1.0 and 17.2.0 are**. Reporter's env: `expo 57.0.25`, `react-native 0.86.3`, New Architecture, EAS Build. https://github.com/invertase/react-native-google-mobile-ads/issues/903
- **Workarounds (per the issue):** pin `17.0.0`, or patch `android/app-json.gradle` (`googleAdsJson` → `googleMobileAdsJson`) and/or guard the `rootProject.ext.googleMobileAdsJson` read in `android/build.gradle` with `has()` via `patch-package`. No released fix exists yet. https://github.com/invertase/react-native-google-mobile-ads/issues/903
- **AdMob needs a dev/EAS build** (`npx expo install` + config plugin) — not Expo Go. https://github.com/invertase/react-native-google-mobile-ads

## (d) Play Data safety + Apple App Privacy for push tokens + AdMob

**Google Play Data safety**

- **Mandatory scope:** all developers with an app on Play must complete the form, **including closed/open/production testing tracks**; apps active *only* on **internal testing** are exempt. You can't skip it by collecting nothing — a "no data" answer still requires a privacy policy link. You are **solely responsible** for including data collected by third-party libraries/SDKs (AdMob). https://support.google.com/googleplay/android-developer/answer/10787469
- **AdMob auto-collects and shares:** IP address (may be used to estimate general location), user product interactions (app launch, taps, video views), diagnostic info (launch time, hang rate, energy), and device/account identifiers (Android **advertising ID**, **app set ID**, signed-in account identifiers). Map these to Play data types: **Device or other IDs**, **Approximate location**, **App activity → App interactions**, **App info and performance → Diagnostics/crash logs**. Purposes: **Advertising or marketing**, **Analytics**, **Fraud prevention, security, and compliance**. https://developers.google.com/admob/android/privacy/play-data-disclosure
- **Push token** is a device-level identifier, so declare **"Device or other IDs"**, collected, transiently used by your backend/app, with the purpose **App functionality** (and **Developer communications** if you push app news); not "sharing" unless you transmit it to a third party. [INFERENCE: mapping from Google's data-type definitions + push-token semantics; the Expo/FCM token is generated per app-install.] https://support.google.com/googleplay/android-developer/answer/10787469
- **Ad ID can be opted out:** developers can prevent collection of the Android ad ID by updating the app manifest; Limited Ads can also suppress ad-ID transmission. This changes whether ad-ID rows are declared. https://developers.google.com/admob/android/privacy/play-data-disclosure

**Apple App Privacy**

- **Mandatory and third-party-inclusive:** App Privacy answers are required for new apps and updates, and must cover "the practices of third-party partners whose code you integrate into your app" (AdMob). You must answer even if the label is "Data Not Collected." https://developer.apple.com/app-store/app-privacy-details/
- **Data types to declare for AdMob:** **Identifiers → Device ID** (advertising identifier / other device-level ID), **Usage Data → Advertising Data** and **Product Interaction**, **Location → Coarse Location** (IP-derived), **Diagnostics → Crash Data / Performance Data**. Purposes: **Third-Party Advertising**, **Analytics**. https://developer.apple.com/app-store/app-privacy-details/ · https://developers.google.com/admob/ios/privacy/data-disclosure
- **Push token:** declare under **Identifiers** (Device ID; a user/account-level token also implies **User ID**) with purpose **App Functionality**. [INFERENCE: mapping from Apple's Identifiers definitions + push-token semantics.] https://developer.apple.com/app-store/app-privacy-details/
- **Tracking / ATT:** if ad data is linked with third-party data for targeted advertising or measured advertising, it falls under **"Data Used to Track You"**, which triggers Apple's **App Tracking Transparency** permission flow (and the App Store privacy label's tracking categories). Guideline **5.1.2** governs data use and sharing. https://developer.apple.com/app-store/app-privacy-details/ · https://developer.apple.com/app-store/review/guidelines/
- **Privacy manifests:** Google Mobile Ads SDK **11.2.0+** ships privacy-manifest declarations, and Apple now requires third-party SDK privacy manifests/signatures; you remain responsible for checking them. https://developers.google.com/admob/ios/privacy/data-disclosure

## Uncertain / version-sensitive

- **Play 12/14 rule:** the threshold has changed before (originally **20 testers / 14 days** when announced in 2023, later reduced to **12/14**). Re-read the support article before you rely on the number; Google can change tester counts or day windows without notice.
- **Organization-account exemption** is grounded in the policy article being scoped to *personal* accounts; Google does not publish a standalone "org accounts are exempt" sentence, so treat it as policy-implied rather than a quoted guarantee.
- **AdMob #903:** open and unreleased as of 2026-09-30. A fix could land in `17.2.x`/`17.3.0` at any time; re-check before building. The `17.0.0` pin is the safe default today.
- **AdMob data lists:** the Android disclosure page reflects the SDK's *latest* version (**25.5.0**) and the iOS page is written around SDK **7.68.0**; the actual AdMob data collection depends on the SDK version + optional features you enable (advanced reporting, mediation adapters), so the disclosure must be re-checked at build time.
- **Push-token data-type mapping** (Play "Device or other IDs", Apple "Device ID"/"User ID") is our inference from the stores' type definitions, not a vendor-documented mapping.
- **FCM credentials:** Expo's guide is current as of the page's July 2026 revision, but EAS CLI prompts and Dashboard paths shift; verify the exact `eas credentials` menu labels when you run them.
- **Expo Go + push:** the removal applies to **Android only from SDK 53** (iOS Expo Go push was affected earlier); both push and AdMob force a development/EAS build regardless.
